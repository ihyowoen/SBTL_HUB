# Legacy Related Lineage Container Initialization — bounded migration contract

**Classification:** `ACTIVE_MIGRATION`  
**Migration family:** `LEGACY_RELATED_LINEAGE_CONTAINER_INIT_V1`  
**Ordinary-run applicability:** `NONE`

## Purpose

This contract permits one separately reviewed canonical-data migration to initialize missing legacy `related_lineage.related_ids` containers that the ordinary card-run engine intentionally refuses to create.

It does not change the ordinary `insert / update / related_add` contract and must not become a general bypass for canonical-data changes.

## Activation

The migration is active only when a pull request contains exactly one repository-relative manifest matching:

`migrations/**/legacy-related-lineage-container-migration.json`

and the dedicated migration validator confirms the declared baseline and exact transformation.

Mere presence of this document does not activate the migration.

## Allowed transformation

For a legacy card whose `related_lineage.related_ids` container is missing or malformed, and whose existing published `related[]` contains no dangling target, the migration may add exactly:

```json
{
  "related_lineage": {
    "related_ids": ["<exact existing related[] values in existing order>"]
  }
}
```

The migration may not invent or infer:

- `relation_type`;
- `reason`;
- `event_stage_relationship`;
- `direction`;
- fresh-follow-up anchors;
- predecessor/successor meaning;
- any new or removed `related[]` edge.

This is neutral container materialization only. It mirrors the already-published `related[]` values so that future separately evidenced `related_add` operations have a valid parent container.

## Mandatory exclusions

A card with any dangling published `related[]` target must not be initialized by this migration. It remains under the dedicated legacy dangling-edge remediation until separately resolved with item-specific evidence and approval.

A card that already has a valid `related_lineage.related_ids` array must remain semantically identical at parsed JSON object level. The validator does not promise preservation of insignificant JSON serialization details such as whitespace or escape spelling.

## Immutable data guarantees

The migration must preserve:

- card count;
- card IDs and order;
- every existing card field other than the allowed `related_lineage` materialization;
- every existing `related[]` value and order;
- all already-valid `related_lineage` objects;
- all dangling legacy cards unchanged;
- zero card deletion;
- zero `related_remove`;
- zero new relation edge.

The document-level `updated` timestamp may change only to the manifest-declared `output_updated` value. Other top-level fields remain unchanged.

## Canonical and lean outputs

`data/cards.full.json` remains the sole canonical inventory. `public/data/cards.json` must be regenerated byte-exactly from the migrated canonical using `scripts/lean_cards.mjs` and must pass the standard full/public validators.

Because `related_lineage` is part of the lean KEEP set, the public projection is expected to change for every initialized card even though visible relation semantics do not change.

## Baseline lock

The manifest must declare:

- `base_main_commit_sha`;
- `base_full_blob_sha`;
- `expected_before`;
- `expected_after`;
- `expected_initialized_count`;
- exact `expected_skipped_dangling_card_ids`;
- `output_updated`.

The PR workflow must compare the declared baseline to the PR base commit and the actual canonical blob. A moved baseline blocks and requires regeneration.

## Completion

This migration is complete only after the canonical full and lean outputs are merged, validators pass, production data remains readable, and the resulting main SHA is recorded in the migration audit/history.

After completion, ordinary runs continue to use the existing card-run engine. Remaining excluded dangling cards stay in separate remediation and are not silently repaired here.
